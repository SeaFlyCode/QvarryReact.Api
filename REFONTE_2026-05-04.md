## 4. 🟠 P1 restants (29)

### Auth (4)
- [ ] **Race condition refresh token côté web** — implémenter mutex (le mobile a `refreshManager`, le web n'en a pas → deux requêtes parallèles peuvent invalider mutuellement les tokens)

- [ ] **2FA endpoints distincts par plateforme** — `/auth/complete-2fa-login` vs `/mobile/2fa/verify-login`. Unifier
- [ ] **403 ambigu** — backend renvoie 403 pour 4 raisons (blocked, unverified, pendingValidation, unauthorized) traitées pareil côté front. Ajouter un champ `reason` ou utiliser des codes HTTP distincts

### Data models — User mobile (1 méta-tâche, ~10 sous-items)

### REST endpoints (3)
- [ ] **`/v1/admin/users/:id/quota`** — endpoint appelé par web mais inexistant. Implémenter dans `adminControllers.ts`
- [ ] **Verbe `PATCH /notifications/read-all` web** — vérifier que l'appel web utilise bien `PATCH` (pas `GET` ou non spécifié)
- [ ] **Photos v1 endpoint** — tester end-to-end `POST /api/v1/points/:id/photo` (upload depuis web)

### Validation / UX (4)
- [ ] **Email temp blocking** — backend a une blocklist (yopmail, etc.). Mobile/web n'ont pas → register casse silencieusement quand l'API rejette. Ajouter check côté front
- [ ] **Phone normalisation mobile** — pas de `libphonenumber-js` côté mobile. User saisie libre → API rejette avec format E.164
- [ ] **Body size 1 MB Express vs 10 MB upload max** — mismatch. Augmenter `express.json` limit ou clarifier que l'upload passe en multipart (pas JSON body)
- [ ] **Rate limit `retryAfter`** — mobile lit, web ignore. Aligner

### Infra (5)
- [ ] **API_URL et WS_URL hardcodés mobile** — dans `src/constants/app.ts`. Switcher sur env vars `EXPO_PUBLIC_API_URL` / `EXPO_PUBLIC_WS_URL` pour pouvoir pointer staging

- [ ] **NEXT_PUBLIC_TURNSTILE_SITE_KEY peut être vide en dev** — Turnstile.tsx log error mais ne bloque pas. Ajouter un fallback ou warning visible
- [ ] **CLIENT_URL vs NEXT_PUBLIC_API_URL alignement** — vérifier en staging que les domaines correspondent (CORS bloqué sinon)
- [ ] **APP_PEPPER hardcoding dev/prod** — risque que la même clé soit utilisée en dev et en prod (isolation cassée)

### WebSocket (4)
- [ ] **`sync_update` dead code** — la méthode existe `webSocketService.ts:2705` mais n'est jamais appelée. Le multi-device sync est probablement non fonctionnel. Auditer l'usage attendu et brancher

## 6. 📐 Recommandation stratégique : éliminer la racine du problème

Toutes les désync identifiées ont **une cause commune** : absence de **single source of truth** sur les contrats. 81 désync trouvées = symptômes. Pour empêcher les futures bombes :

### Option A — Monorepo + package `@qvarry/contracts` (recommandé)
- Restructurer en monorepo (Turborepo / Nx / pnpm workspaces)
- Package `contracts` qui exporte : types modèles, enums partagés, schémas Zod, liste des routes typées
- Backend, mobile, web l'importent → toute désync = erreur TS
- Effort one-shot ~1 semaine, gains permanents

### Option B — OpenAPI + codegen
- Générer spec OpenAPI depuis le backend (express-openapi-validator ou Zod-to-OpenAPI)
- Codegen des clients TypeScript pour mobile et web
- Pas de monorepo nécessaire mais codegen à maintenir

### Option C — Contract testing (Pact)
- Tests d'intégration en CI qui valident les contrats
- Détecte les drifts mais ne les empêche pas en local
- À combiner avec A ou B, pas seul

**Recommandation finale** : **Option A**. Le monorepo apporte aussi des bénéfices secondaires (CI mutualisée, refacto cross-projet plus simples, partage de helpers comme la validation password).
